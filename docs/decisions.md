[Phase 00] Decision: The repository is public; `*:Zone.Identifier` (Windows download metadata) is gitignored as an OS file | Reason: the owner's choice, matching the backend; free rulesets on a personal account | Alternatives considered: private
[Phase 01] Decision: Scaffolded from the official template (`npm create vite@9.2.1 -- --template react-ts`), then pinned exactly to the latest stable releases on npm (2026-09-30): vite 8.3.1, @vitejs/plugin-react 6.1.1, react and react-dom 19.3.0, @types/react and @types/react-dom 19.3.0, typescript 7.0.2, @types/node 24.19.0 | Reason: CLAUDE.md asks for current stable releases with exact pins; the template's `^`/`~` ranges would drift | Alternatives considered: the template's ranges as generated
[Phase 01] Decision: TypeScript 7.0.2 (the native compiler), not the template's `~6.0.2` | Reason: 7.0.2 is npm's `latest`, no peer dependency excludes it, and `tsc -b` on it enforces this project's flags (checked with a probe file that failed on `noUncheckedIndexedAccess` and `noImplicitOverride`) | Alternatives considered: typescript 6.0.3, the template's line (fallback if a later tool needs the TypeScript JS API that 7 does not ship)
[Phase 01] Decision: The template's oxlint, `lint` script and `.oxlintrc.json` are dropped, as are its demo files, favicon and CSS | Reason: lint is Phase 4's technology, styling Phase 9's; this phase keeps browser defaults | Alternatives considered: keeping oxlint unused until Phase 4
[Phase 01] Decision: Node is pinned to 24.21.0 (the Active LTS) in `.nvmrc`, `engines` is `^24.21.0`, and `.npmrc` sets `engine-strict=true` and `save-exact=true` | Reason: on this machine a non-interactive WSL shell finds the Windows npm under `/mnt/c` first; engine-strict turns that into a clear failure; save-exact keeps every future install pinned | Alternatives considered: `.nvmrc` = `lts/*` (moves on its own)
[Phase 01] Decision: `typecheck` = `tsc -b`, `build` = `vite build`, `verify` = `npm run typecheck && npm run build` | Reason: the root tsconfig is a solution file with `files: []`, so `tsc --noEmit` alone would check nothing; `tsc -b` checks both projects; keeping it out of `build` avoids type checking twice in `verify` | Alternatives considered: the template's `build` = `tsc -b && vite build`
[Phase 01] Decision: `vite.config.ts` reads `API_TARGET` with `loadEnv(mode, cwd, '')` (shell environment first, then `.env`), default `http://localhost:8080`; one proxy object serves both `server` and `preview`; ports use `strictPort` | Reason: makes `.env.example`'s `API_TARGET` work from a `.env` file too, while only `VITE_*` values ever reach the browser; a busy port fails loudly instead of moving (Playwright will rely on 4173) | Alternatives considered: `process.env.API_TARGET` alone (ignores `.env`)
[Phase 01] Decision: Every product request sends its own `X-Correlation-Id` (a UUID); the error state shows the response's id for a 5xx, or the sent id when no response arrived | Reason: the gateway reuses a caller id matching `[A-Za-z0-9_-]{8,64}` (`CorrelationId.sanitize`, backend), so the id the user reports is the one in the backend logs, and a network failure still has a reference | Alternatives considered: showing an id only when a response carried one (none for network errors)
[Phase 02] Decision: Test stack pinned to npm's `latest` on 2026-09-30: vitest and @vitest/coverage-v8 5.0.3, jsdom 30.1.1, @testing-library/react 16.3.3, @testing-library/dom 10.4.2, @testing-library/jest-dom 7.0.1, @testing-library/user-event 14.6.7, msw 3.0.1 | Reason: current stable releases; their peer ranges accept Vite 8, React 19, TypeScript 7 and Node 24.21 | Alternatives considered: happy-dom (faster, less complete DOM)
[Phase 02] Decision: MSW's unhandled-request option is `onUnhandledFrame: 'error'`, not the phase file's `onUnhandledRequest` | Reason: MSW 3 renamed it (a "frame" is an HTTP request or a WebSocket event); the old key type-fails but is silently ignored at runtime, leaving the default `'warn'`. A probe test proved an unmocked fetch now fails | Alternatives considered: none (same intent, new name)
[Phase 02] Decision: Vitest is configured in `vite.config.ts` (not a separate `vitest.config.ts`), without `globals`; tests import `describe`/`it`/`expect` and the setup calls `cleanup()` | Reason: one config means tests resolve `@/` and JSX exactly like the app; explicit imports keep test globals out of app code's types | Alternatives considered: `globals: true` with `vitest/globals` types
[Phase 02] Decision: Coverage (V8) thresholds are the measured values (statements 91.11, branches 74.19, functions 91.66, lines 97.5), checked by `npm run test:coverage`; `verify` runs plain `vitest run` | Reason: the phase file defines `verify`'s `test` as `vitest run`; the floor only rises (Phase 5's CI is the natural place to enforce it on every PR) | Alternatives considered: coverage inside `verify` now
